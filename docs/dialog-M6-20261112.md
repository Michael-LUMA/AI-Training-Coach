## 2. 实现内容

- 新增 `dialog_store.py`：`save_turn`、`get_recent`、`delete_one`、`delete_all`，另提供事务化 `save_exchange` 与有界 `list_turns`。
- 实际入口在 `coach_server.py`，不是任务包写的 `ride_server.py`。身份验证与存取编排放在路由上游，builder 不读取身份或数据库。
- `db.py` 增加 `dialog_turns` 表、用户时间索引。每条消息有 ID、所属用户、exchange_id、角色、内容、UTC 时间；exchange_id 用于可靠配对。角色限定 user/mark，关联用户外键。
- `/api/coach/ride/chat` 带合法云 token 时：读云端最近对话，经 M5 预算后以 history 传入 builder；成功后把用户问题与最终回答在一个事务中写入。
- 覆盖普通回答、天气确定性回答、实时回答，以及缺实时事实时的诚实模板返回。失败、被安全校验拒绝或没有 speech 的回答不入库。
- 云端按用户隔离，不读取匿名 conv_id 历史、不回退共享本机数据。匿名模式仍保留原三轮内存 TTL。
- 读取最近一小时内、非未来的**最多五个完整问答轮次**，不是五条消息；旧到新注入。单条删除导致不完整的一轮不会再进入上下文。
- 最近五轮是读取上限而不是强制塞满：原有 ≤800 记忆预算同时检查上下文及 builder 投影，按完整组/完整旧轮舍弃，不截断字符串、JSON 或单位；长回答可能使实际注入少于五轮。
- 不改 system prompt、builder 签名、LLM 传输逻辑、数字验证规则或 qwen-max 配置；recent_dialog 只进入 user facts，不注册为当前数值来源。
- 旧 history 校验最多三轮、每个回答 300 字，现支持五轮、回答最多 480 字，以兼容原 general builder 已允许的 480 字；各 builder 自身输出长度限制不变。
- 只存通过校验的问答文字；问题最多 200 字，回答最多 480 字。不接收原始音频、轨迹或任意扩展字段。这里是文字类型/大小限制，并不意味着用户主动说出的敏感内容已被自动脱敏。

## 3. HTTP 接口契约

这两个新接口保留私测访问限制、同源检查、`X-Coach-Token` 浏览器门禁与限流，另使用 JSON 中的云 `token` 推导 user_id。两种 token 不可互换，拒绝客户端指定 user_id。响应保留 `Cache-Control: no-store`。

### 查看 / 导出本用户对话

`POST /api/dialog/list`

```json
{"token":"<cloud-token>","limit":100}
```

- `limit` 按消息条数计，默认 100，上限 2000。
- 返回 turns（每条含 id/exchange_id/role/content/created_at）、total_messages、total_rounds、has_more、max_rounds、export_required。
- 返回选定的最新消息，结果按旧到新排列。
- 完整导出本用户对话：`{"token":"<cloud-token>","export":true}`。最多 2000 条消息，仍为有界 JSON；本轮不提供搜索或 M7 的全用户数据导出。

### 单条 / 全部硬删除

`POST /api/dialog/delete`

```json
{"token":"<cloud-token>","id":"<message-id>"}
```

或

```json
{"token":"<cloud-token>","all":true}
```

返回 `{"deleted":N}`。SQL 直接 DELETE，无软删标记。其他用户的 ID 不会删除任何数据，重复删除返回 0。单条删除按消息 ID；该轮剩余消息仍可查看，但完整轮上下文不再包含它。

## 4. 1000 轮保留策略与导出机会

“一轮”由同一个 exchange_id 下的用户消息及 Mark 消息组成；不完整消息也占一个轮次配额，防止通过半轮突破限制。

1. 每用户最多 1000 轮，即完整情况下 2000 条消息。
2. 容量满且未确认清理时，在正常模型调用前检查并返回 HTTP 409、`dialog_export_required`，不静默丢弃旧内容。
3. 用户可先通过 `/api/dialog/list` 的 `export:true` 完整取出对话。
4. 用户选择允许清理后，下一次 chat 显式传 `"dialog_prune_confirmed":true`；事务内自动删除足够数量的最旧完整 exchange，再插入新一轮。
5. 确认只对当前请求有效，不偷偷形成永久同意；接口不强制证明用户已下载导出文件，用户可自主选择直接确认清理。
6. 写入与删除在同用户行锁下执行；清理、新问题和新回答同事务提交，失败全部回滚。保存阶段会复查容量，防止预检后的并发突破上限。
7. 极端并发下，另一个请求可能在预检后占满配额，保存阶段仍可能返回 409。模型回答后数据库不可用则返回脱敏 503，不谎称已保存；本轮没有自动重试/付费重试机制。
