This notice describes the current single-user, local pilot, not a hosted service. It is not a claim that public-launch compliance review is complete.

What is stored and processed

You paste your own Intervals.icu API key. The pilot stores it in a dedicated local SQLite database, encrypted by the available backend. Saving is refused if no encryption backend is available. Windows uses current-user DPAPI. The alternative masterkey backend is a constrained, unaudited standard-library construction, not audited encryption; keep the master key secret and separate from database backups.

Only after you request an activity list or review does the pilot send authenticated requests to Intervals.icu. It processes activity details and streams, sport settings such as FTP and zones, and wellness data such as training load, sleep or resting heart rate where available.

Activity data and generated reviews are held temporarily in process memory and the current browser page. This version has no persistent activity-data cache or review database. Responses use no-store; it does not deliberately save activity data in browser storage. It cannot guarantee erasure of OS memory, browser session recovery, or files you export yourself.

If you submit the optional waitlist, your lowercase email address and initial submission time are stored in a separate local waitlist.db beside the credential database. This file is not encrypted by the credential keystore and relies on filesystem permissions. It records your opt-in for product updates, but this pilot sends no email and does not synchronize the list to a hosted service. First and repeat submissions receive the same acknowledgement. Remove this file and its SQLite sidecars with the server stopped to delete waitlist records; remove backups separately.

Purpose and limits

Data is used to show your activities and produce the review you request. We do not sell your data and do not use it to train models. This pilot has no analytics, advertising SDKs, external fonts or CDN. Reviews are rule-based; no external AI model receives your activity data.

Third parties

The current external integration is the Intervals.icu API, which receives your API key and requested activity identifiers/date ranges under its own policies. An optional Creem webhook skeleton can accept signed server callbacks when the operator configures a secret. It stores event identifiers/types/timestamps and subscription identifiers, customer email when supplied, status and update time in a separate local billing.db. It does not store raw callback bodies, card details or the webhook secret. Billing metadata is not encrypted by the credential keystore; remove this file and its SQLite sidecars with the server stopped to delete it. There is no checkout, charging or paid-access enforcement in this pilot; no outbound Creem request is made. Provider terms, operator identity and launch data handling still require review before payments are enabled. Your browser, operating system, network and Intervals.icu remain outside this local app's control.

Retention and deletion

The saved key remains until you remove the local store. This version has no in-app delete button. To delete the saved key and all app-managed persistent local data: stop the server, close the app's browser pages, then manually delete the dedicated .runtime/coach/ directory under the application directory (or the dedicated store location configured by your operator), including the SQLite database and any journal, WAL or SHM files. Do not delete unrelated directories. Restarting should show no connected key.

Close the browser pages and stop the process to release the temporary activity cache and reviews. Remove your own exports and backups separately; deleting the local store does not delete backups, guarantee physical secure erasure, or remove data held by Intervals.icu. Revoke the API key in Intervals.icu if you no longer want it usable. A separately provisioned master key is not removed by deleting SQLite.
